## Q1. Status of arthenica ffmpeg-kit and the Flutter community forks (maintenance, versions, SPM, size, LGPL vs GPL, GPL-only filters, App Store LGPL)

### Takeaway
The upstream arthenica FFmpegKit is officially retired, and its GitHub repo was archived on 2 July 2026. In October 2026 the practical Flutter options are community forks. HOOKKADR's current `ffmpeg_kit_flutter_new_full` (v2.5.7, FFmpeg 8.1.2, about 2026-10-06) is actively published and LGPL-only, and its iOS build ships as dynamic frameworks. None of the filters HOOKKADR uses is GPL-gated. The main risk is the bus factor: a single maintainer controls the binaries.

### Cited Findings
**Upstream arthenica/ffmpeg-kit**
- The repo is "archived by the owner on Jul 2, 2026" and read-only. The README section "Update (July 2026)" says "`FFmpegKit` has been officially retired. Historical releases and documentation remain available in this repository." — [GitHub arthenica/ffmpeg-kit, accessed 2026-10-14](https://github.com/arthenica/ffmpeg-kit)
- The README points to "FFmpegKitNext", a continuation by the original author that is distributed **as source only**, and to community forks in package managers. The last release-table entries are Flutter/React Native 6.0.3 (Sep 19, 2023) and Android/Apple 6.0 (Aug 21, 2023). — [GitHub arthenica/ffmpeg-kit](https://github.com/arthenica/ffmpeg-kit)
- A web search for "FFmpegKitNext" returned no page of its own, so its repo URL and status could not be confirmed. A Sonatype Central result for `com.arthenica/ffmpeg-kit-min-gpl` is titled "No Results Found", which fits the Maven artifacts having been removed but does not prove it. — [search result: central.sonatype.com](https://central.sonatype.com/artifact/com.arthenica/ffmpeg-kit-min-gpl)

**Fork family `ffmpeg_kit_flutter_new*` (publisher antonkarpenko.com, GitHub sk3llo/ffmpeg_kit_flutter)**
- `ffmpeg_kit_flutter_new` **4.6.7**, published about 2026-10-06 by verified publisher antonkarpenko.com, bundles **FFmpeg 8.1.2**. It supports Android API 24+, iOS 14.0+, macOS 10.15+, Windows 10+ x86_64 and Linux x86_64. It has 204 likes, 160 pub points and 41.1k downloads. — [pub.dev ffmpeg_kit_flutter_new, accessed 2026-10-14](https://pub.dev/packages/ffmpeg_kit_flutter_new)
- **Important licensing trap:** the base package `ffmpeg_kit_flutter_new` is the **full-gpl** variant. It adds vid.stab, x264, x265 and xvidcore, so "apps using it are distributed under GPL 3.0". The other variants are min, min-gpl, https, https-gpl, audio, video, full and full-gpl. — [pub.dev ffmpeg_kit_flutter_new](https://pub.dev/packages/ffmpeg_kit_flutter_new); [GitHub sk3llo/ffmpeg_kit_flutter README](https://github.com/sk3llo/ffmpeg_kit_flutter)
- `ffmpeg_kit_flutter_new_full` is at **2.5.7** (about 2026-10-06), uses FFmpeg 8.1.2, is LGPL-3.0, and "contains no GPL components". It includes every supported library except x264, x265, xvidcore and vid.stab, for example dav1d, gnutls, libvpx, libwebp, libass, opus, lame and zimg. — [pub.dev ffmpeg_kit_flutter_new_full](https://pub.dev/packages/ffmpeg_kit_flutter_new_full)
- **Swift Package Manager:** iOS and macOS support SPM on Flutter 3.24+ as well as CocoaPods, both with "checksum-pinned XCFrameworks". Older 2.2.x score pages showed no SPM support, and 2.4.x pages show it as SPM-ready. — [pub.dev ffmpeg_kit_flutter_new_full](https://pub.dev/packages/ffmpeg_kit_flutter_new_full); [pub.dev score pages (search result)](https://pub.dev/packages/ffmpeg_kit_flutter_new_full/score)
- The repo sk3llo/ffmpeg_kit_flutter has 185 stars, 122 forks, 80 commits and 5 open issues. It is maintained by a single individual account, with support through Discord, GitHub issues and Buy Me a Coffee. Its Releases section is empty, and the page shows no last-commit date. — [GitHub sk3llo/ffmpeg_kit_flutter, accessed 2026-10-14](https://github.com/sk3llo/ffmpeg_kit_flutter)
- Hardware acceleration: VideoToolbox is used on iOS and macOS, and the Android build lists MediaCodec among its system libraries. — [pub.dev ffmpeg_kit_flutter_new_full](https://pub.dev/packages/ffmpeg_kit_flutter_new_full)

**GPL-only parts of FFmpeg (current master LICENSE.md)**

- **GPL external libraries:** avisynth, frei0r, libcdio, libdavs2, librubberband, **libvidstab**, **libx264**, **libx265**, libxavs, libxavs2 and **libxvid**. smbclient is GPLv3. **Nonfree, so not redistributable:** Fraunhofer FDK AAC and OpenSSL. — [FFmpeg LICENSE.md](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/LICENSE.md)
- drawtext depends on libfreetype, not on GPL (`drawtext_filter_deps="libfreetype"`). — [FFmpeg-devel archive (search result, older)](https://lists.ffmpeg.org/pipermail/ffmpeg-cvslog/2012-October/056560.html)

**LGPL compliance (ffmpeg.org/legal.html)**
- The checklist says: compile without `--enable-gpl` and `--enable-nonfree`; link dynamically; distribute the source of the exact binaries and document the configure line; add attribution in the About box and EULA; remove any ban on reverse engineering; do not rename or obfuscate library names; repeat for each LGPL external library. — [ffmpeg.org/legal.html, accessed 2026-10-14](https://ffmpeg.org/legal.html)
- On iOS and the App Store, the only primary material found is old. In FFmpeg trac #1229 (2012, closed wontfix), a maintainer said that LGPL compliance means providing the exact FFmpeg source and, without dynamic linking, providing object files for relinking. A 2010 checklist on the user list said that because "dynamic linking is not allowed by Apple", apps must link statically and ship object files. — [trac.ffmpeg.org #1229 (2012)](https://trac.ffmpeg.org/ticket/1229); [FFmpeg-user 2012](https://ffmpeg.org/pipermail/ffmpeg-user/2012-June/007469.html). An HN commenter argues that App Store terms may conflict with the LGPL. That is opinion. — [HN via brianlovin.com](https://brianlovin.com/hn/38964972)

### Inferences
- HOOKKADR's current filter set (xfade, zoompan, drawtext, lutyuv, hue, colorbalance, overlay, sidechaincompress, amix) contains **no GPL-only filters**. The FFmpeg GPL list names **eq**, boxblur, hqdn3d, smartblur, perspective, delogo and others, so the grade must keep using lutyuv/hue/colorbalance (or curves/lut3d) and never `eq`. A CI guard that greps `render_plan.dart` for the GPL filter names would be cheap insurance.
- **Never switch to the base `ffmpeg_kit_flutter_new` package** (it is full-gpl) or to any `-gpl` variant. Doing so would turn the whole app into GPL-3.0 distribution.
- The 2010–2012 claim that "dynamic linking is not allowed on iOS" is outdated, because the iOS build HOOKKADR actually ships uses dynamic frameworks **[local check]**. That satisfies the dynamic-linking item. HOOKKADR still has to (a) publish the FFmpeg source and configure line for the exact build (the fork's builder sources plus the configure string), (b) add attribution in the About/Licenses screen, and (c) handle the fact that the build uses `--enable-version3`. LGPL**v3** brings GPLv3's "Installation Information" clause for user products, and that interacts with iOS code signing. This is a legal question with no primary source found here (see Gaps).
- Bus-factor risk: one individual maintainer publishes the binaries for all eight variants. Pinning exact versions and caching the XCFrameworks/AARs, or building them from the fork's sources, would reduce supply-chain risk. `ffmpeg_kit_extended_flutter` (FFI and build hooks) is a second-source option, but it is younger (0.x).
- `libtesseract`, `libsrt`, `libaom` and `libxml2` are compiled into the "full" variant and add size without serving HOOKKADR's needs. A custom LGPL build with only libfreetype, fribidi, harfbuzz and fontconfig (for drawtext/libass), VideoToolbox/MediaCodec and dav1d could plausibly cut the binary substantially. This is not measured.

### Gaps
- The exact retirement chronology could not be verified. From background knowledge only (not confirmed this session), arthenica may have announced retirement and removed binaries from Maven Central, CocoaPods and pub.dev during 2025, before the July 2026 archive. The current README shows only the July 2026 update.
- No FFmpegKitNext URL, license or activity data was found.
- No commit dates or release cadence could be read for sk3llo/ffmpeg_kit_flutter. Activity is inferred only from pub.dev publish dates.
- No App Store–specific legal guidance (from Apple, FSF or FFmpeg) dated after 2012 was found on LGPLv3 plus App Store distribution. The project needs a lawyer's opinion.
- No official binary-size figures exist for `ffmpeg_kit_flutter_new_full`. The only figures available are the local measurement and the extended-fork table.
- The license status of zoompan, xfade and sidechaincompress was confirmed only by their absence from the GPL list in LICENSE.md, not by reading per-file headers.

## Q2. H.264 / HEVC / AAC patent licensing: platform hardware encoders vs bundled software encoders

### Takeaway
FFmpeg grants no patent licenses and warns that commercial products carry patent risk. The source found here (an undated Via LA rate card) lists a royalty-free tier for the first 100,000 units. Cisco covers H.264 royalties only for its own downloaded OpenH264 binary, never for builds compiled from source, and HOOKKADR's iOS FFmpeg build compiles in libopenh264 **[local check]**. Using the OS encoders (VideoToolbox, MediaCodec) is the lower-risk path, but no primary source was found confirming that OS vendors' licenses cover third-party apps.

### Cited Findings
- FFmpeg's legal page says it does not know whether FFmpeg uses patented algorithms, that standards like H.264 carry patent notices, that private use carries "remarkably little reason to be concerned" while commercial products carry risk, and that MPEG LA is "vigilant and diligent about collecting for MPEG-related technologies". — [ffmpeg.org/legal.html](https://ffmpeg.org/legal.html)
- Via LA's AVC/H.264 portfolio license covers encoders and decoders, including mobile devices. The rate card (undated, read from a search snippet, so it may be outdated) lists $0.00 for the first 1–100,000 units, then $0.20 per unit up to 5M and $0.10 beyond. — [Via LA AVC/H.264 (search result)](https://www.via-la.com/licensing-2/avc-h%20264/)
- A historical analysis (around 2003, quoted in later coverage) says the AVC licenses "do not make any distinction for products offered for free". MPEG LA has long waived royalties for free-to-end-user internet video. — [MPEG-4 AVC License Proposals (mpegif.org, about 2003)](https://mpegif.org/MPEG-4%20AVC%20License%20Proposals1.pdf); [TV Technology (older)](https://www.tvtechnology.com/news/mpeg-la-extends-free-use-of-h264)
- HEVC Advance (now Access Advance) licenses encoders and decoders "in devices, software, or through Cloud Based Services", with one royalty per device or software copy at first sale. Its 2016 software carve-out exempts only application-layer software downloaded after device sale where HEVC runs "fully executed in software on a general purpose CPU". — [Access Advance: what we license](https://accessadvance.com/topic-what-do-we-license/); [Beamr blog, 2016-11-30](https://blog.beamr.com/2016/11/30/patent-pool-hevc-advance-responds-announces-royalty-free-hevc-software/)
- OpenH264 FAQ: "Cisco is only covering the licensing fees for its own binary module." A team that uses the source code "is responsible for paying all applicable license fees". It also says "iOS does not allow for applications to fetch and install modules from the Internet" and points to Apple's VideoToolbox for H.264 on iOS 8+. The page is undated. — [openh264.org FAQ, accessed 2026-10-14](https://www.openh264.org/faq.html)
- **[local check]** HOOKKADR's iOS FFmpeg build includes `--enable-libopenh264` and `--enable-audiotoolbox`. FDK-AAC is nonfree and not redistributable ([FFmpeg LICENSE.md](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/LICENSE.md)), so AAC encoding comes from FFmpeg's native `aac` encoder or from AudioToolbox (`aac_at`).

### Inferences
- HOOKKADR currently encodes with `h264_videotoolbox` and `h264_mediacodec`. That keeps encoding inside the OS-supplied codec, which is the commonly assumed safer posture. The source-built **libopenh264 encoder** bundled in the iOS binary is the item to avoid: according to Cisco's FAQ, a source-compiled OpenH264 is not covered by Cisco's royalty payment. The app should never fall back to `libopenh264` (or `libx264`, which is also GPL) when hardware encoding fails. A custom build without libopenh264 would remove the question.
- Native engines (AVFoundation and Media3 Transformer) also encode through OS codecs (VideoToolbox and MediaCodec), so moving to them does not change the patent posture compared with FFmpeg's hardware-encoder path.
- For AAC, `aac_at` (AudioToolbox) on iOS and MediaCodec AAC on Android keep audio encoding within the OS as well. FFmpeg's native `aac` encoder is a bundled software encoder.

### Gaps
- No primary source was found from Apple, Google, Via LA or Access Advance stating whether an app that calls VideoToolbox or MediaCodec is covered by the OS vendor's codec license. This needs counsel or direct confirmation from the pools.
- Current (2026) Via LA and Access Advance terms for free or freemium mobile apps were not retrieved. A localized report mentioned higher Via LA streaming fees, but it was undated and not verified.
- The AAC patent pool (Via LA AAC) was not researched.

## Q3. iOS native: AVFoundation composition, custom compositors, Core Image/Metal, export, HDR, bridging, real-time preview

### Takeaway
AVFoundation's `AVVideoComposition` with a `customVideoCompositorClass` is the one object that drives **both** real-time preview (`AVPlayerItem`) and export (`AVAssetExportSession` / `AVAssetReaderVideoCompositionOutput`), as well as thumbnails (`AVAssetImageGenerator`). On iOS that is the structural basis for preview and export parity. The compositor protocol has explicit HDR and wide-color opt-ins. Since iOS 26, `BGContinuedProcessingTask` lets a user-started export continue in the background, with an optional GPU entitlement.

### Cited Findings
- `AVVideoCompositing` is "A protocol that defines the methods custom video compositors must implement" (iOS 7.0+). AVFoundation creates and uses the compositor whenever an `AVPlayerItem`, `AVAssetExportSession`, `AVAssetImageGenerator` or `AVAssetReaderVideoCompositionOutput` has a `videoComposition` whose `customVideoCompositorClass` is non-nil. — [Apple docs: AVVideoCompositing (JSON), accessed 2026-10-14](https://developer.apple.com/documentation/avfoundation/avvideocompositing)
- Required members are `sourcePixelBufferAttributes`, `requiredPixelBufferAttributesForRenderContext`, `renderContextChanged(_:)` and `startRequest(_:)` ("create a new pixel buffer composed asynchronously from a collection of sources"). Optional members include `cancelAllPendingVideoCompositionRequests()`, `anticipateRendering(using:)` and `prerollForRendering(using:)` with `AVVideoCompositionRenderHint`. — [Apple docs: AVVideoCompositing](https://developer.apple.com/documentation/avfoundation/avvideocompositing)
- The HDR and color properties are `supportsHDRSourceFrames` ("handles source frames that contain high dynamic range (HDR) properties"), `supportsWideColorSourceFrames`, `canConformColorOfSourceFrames` and `supportsSourceTaggedBuffers`. — [Apple docs: AVVideoCompositing](https://developer.apple.com/documentation/avfoundation/avvideocompositing)
- `AVAssetExportSession` exposes `videoComposition`, `customVideoCompositor`, `audioMix`, `audioTimePitchAlgorithm`, `allowsParallelizedExport`, `canPerformMultiplePassesOverSourceMediaData`, `fileLengthLimit`, `timeRange`, and resumable export (`configureForResumableExport()` / `ResumptionState`). The modern API is `export(to:as:isolation:)` (async throws) with `states(updateInterval:)` as an AsyncSequence. `exportAsynchronously(completionHandler:)`, `status`, `progress`, `error`, `outputURL` and `outputFileType` are **deprecated**. — [Apple docs: AVAssetExportSession (JSON), accessed 2026-10-14](https://developer.apple.com/documentation/avfoundation/avassetexportsession)
- `BGContinuedProcessingTask` ("A task that starts in the foreground and can continue running in the background as needed") requires **iOS/iPadOS 26.0**. The system shows progress in a Live Activity, and the user can cancel. The implementation must report progress through `ProgressReporting`. The system "prioritizes the termination of tasks that reflect minimal or no progress". GPU use requires the entitlement `com.apple.developer.background-tasks.continued-processing.gpu` ("Background GPU Access"). — [Apple docs: BGContinuedProcessingTask (JSON), accessed 2026-10-14](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)
- An Apple DTS engineer said the API is for finishing high-priority work the user requested, not for deferring work. One developer reported that background GPU access did not work for their video export on iOS 26 (anecdotal). — [Apple Developer Forums thread 806002](https://developer.apple.com/forums/thread/806002)
- Pigeon 29.0.8 (about 2026-10-10, publisher flutter.dev) generates type-safe channel code for Swift, Objective-C, Kotlin, Java, C++ and GObject. It supports `@async` (Swift async, Kotlin suspend), `@FlutterApi()` host-to-Dart calls, and `@EventChannelApi` streams (Swift, Kotlin and Dart only). — [pub.dev pigeon, accessed 2026-10-14](https://pub.dev/packages/pigeon)

### Inferences
- An iOS backend could compile HOOKKADR's `EditPlan` into an `AVMutableComposition` (trim and concat via track time ranges, plus audio tracks) and an `AVMutableVideoComposition` whose custom compositor applies all video effects in Metal or Core Image: grade (lutyuv/hue/colorbalance equivalents), xfade-style transitions, zoompan transforms and overlays. The same compositor would serve `AVPlayerItem` preview, `AVAssetImageGenerator` timeline thumbnails and export, which gives exact parity on iOS by construction.
- Audio ducking (`sidechaincompress`) has no direct AVFoundation equivalent in the sources reviewed. `audioMix` volume ramps can approximate it by pre-computing duck envelopes from the voice track. True compression would need an audio processing tap or AVAudioEngine offline render (not verified here).
- HOOKKADR's minimum is iOS 16, so `BGContinuedProcessingTask` can only be an iOS 26+ enhancement, and the deprecated-but-available AVAssetExportSession APIs remain needed for iOS 16–17. A Flutter bridge would use Pigeon `@async` for start, cancel and probe calls, plus `@EventChannelApi` for progress.
- The preview surface would be the AVPlayer output rendered into a Flutter `Texture`. That is how `video_player_avfoundation` already works, through `AVPlayerItemVideoOutput` to a CVPixelBuffer to a FlutterTexture (background knowledge, not re-verified this session).

### Gaps
- No primary source was retrieved on AVFoundation 4K60, HEVC or HDR export preset specifics, `AVAssetWriter` HDR settings, or `AVVideoCompositionCoreAnimationTool` limits. From background knowledge only: the Core Animation tool is export-only, and preview of layer overlays needs `AVSynchronizedLayer`, so a custom compositor that draws text as textures avoids that split.
- No measurements were found for custom-compositor real-time performance on older devices (iPhone XS/11 class on iOS 16).
- No source was found for the background time available to `beginBackgroundTask` on iOS 16–25.

## Q4. Android native: Media3 Transformer and Effect, CompositionPlayer, versions, API levels, fragmentation

### Takeaway
Media3 is at **1.11.1 (2026-09-10)**. Transformer requires API 23+ (Media3 minSdk is 23 since 1.9.0), which fits HOOKKADR's minSdk 30. A single `Composition` drives both `Transformer` export and `CompositionPlayer` preview, and the effect library covers HOOKKADR's grade, overlay, crop, scale and speed needs. Three caveats remain: **CompositionPlayer is still `@ExperimentalApi`**, multi-video-sequence preview (PiP or overlapping layers) is "in active development", and **crossfading is "not yet supported"**, so xfade-style transitions need custom GL work.

### Cited Findings
- The latest stable is Media3 **1.11.1, released 2026-09-10**. The 1.11.0 pre-releases ran from alpha01 (2026-06-24) to beta01 (2026-07-07) to rc01. — [androidx Media3 release notes, accessed 2026-10-14](https://developer.android.com/jetpack/androidx/releases/media3)
- 1.11.0 added pitch-preserving time-stretch through `EditedMediaItem.Builder#setSpeed(SpeedParameters)`, fixed over-reported `ExportResult.fileSizeBytes`, fixed a player freeze on seek in `FinalShaderProgramWrapper`, and added `OggMuxer`, `WavMuxer` and IAMF in `Mp4Muxer`. — [Media3 release notes](https://developer.android.com/jetpack/androidx/releases/media3)
- 1.10.0 lets `setFrameRate()` cap the output frame rate, moved `LottieOverlay` to the new `media3-effect-lottie` module, and added `EditedMediaItem.removeVideo` support to CompositionPlayer. — [Media3 release notes](https://developer.android.com/jetpack/androidx/releases/media3)
- 1.9.0 made `InAppMp4Muxer` the default, added `EditedMediaItem.Builder#setSpeed()` (deprecating `Effects#createExperimentalSpeedChangingEffects()`), replaced `forceAudioTrack`/`forceVideoTrack` with `trackTypes`, published CompositionPlayer under **`@ExperimentalApi`**, added speed changes in secondary sequences, and **raised minSdk to 23**. — [Media3 release notes](https://developer.android.com/jetpack/androidx/releases/media3)
- Transformer supports Android 6.0 (API 23)+. It uses MediaCodec for hardware decode and encode, OpenGL for graphical modifications, and a customizable encoder factory. It "includes workarounds for more consistent behavior across Android versions and devices" and is "under active development". — [developer.android.com Media3 Transformer, accessed 2026-10-14](https://developer.android.com/media/media3/transformer)
- A Composition is "a timeline that holds one or more sequences". `EditedMediaItem` is media plus `Effects`, and `EditedMediaItemSequence` is an ordered track. Multiple sequences "can be arranged to play sequentially or can overlap in time, allowing for overlaid layouts like picture-in-picture". Sequences can be audio-only, for example background music with `setIsLooping(true)`. Supported uses: concatenating audio, image and video; background audio; effects; HDR-to-SDR tone mapping. **"Crossfading video or audio tracks is not yet supported."** — [developer.android.com Composition, accessed 2026-10-14](https://developer.android.com/media/media3/transformer/composition)
- Transformations include `ClippingConfiguration` trim, `Presentation.createForHeight()`, `ScaleAndRotateTransformation`, and custom effects that the framework "converts ... into a sequence of GL shader programs". Video effects also preview in ExoPlayer through `ExoPlayer.setVideoEffects`. Audio effects are `AudioProcessor` chains on PCM. Experimental: edit-list trimming and trim optimization (single-asset MP4 only). — [developer.android.com Transformations, accessed 2026-10-14](https://developer.android.com/media/media3/transformer/transformations)
- **CompositionPlayer** "renders a `Composition` in real time". "The same `Composition` can be used for both preview and export." It is in "early preview" and `@ExperimentalApi`. Supported: single asset, single sequence, and one video sequence plus one audio sequence. **In active development:** multi-asset preview with multiple video sequences (PiP, side-by-side, grid) and custom graphics engines. Constraints: `MultipleInputVideoGraph.Factory` is required if more than one sequence has video or image items, every item needs an explicit duration, access is single-threaded, and repeat mode is limited to OFF or ALL. — [developer.android.com CompositionPlayer, accessed 2026-10-14](https://developer.android.com/media/media3/transformer/compositionplayer)
- The `androidx.media3.effect` source tree (release branch) contains Brightness, Contrast, **HslAdjustment**, **RgbAdjustment**, RgbFilter, RgbMatrix, **SingleColorLut**, ColorLut, Crop, Presentation, ScaleAndRotateTransformation, MatrixTransformation, GlMatrixTransformation, **TextOverlay**, **BitmapOverlay**, DrawableOverlay, CanvasOverlay, **OverlayEffect**, AlphaScale, GaussianBlur, LanczosResample, SpeedChangeEffect, FrameDropEffect, **GlEffect**, GlShaderProgram, BaseGlShaderProgram, DefaultVideoCompositor, MultipleInputVideoGraph and SingleInputVideoGraph. No transition or crossfade class was found. — [GitHub androidx/media effect sources, accessed 2026-10-14](https://github.com/androidx/media/tree/release/libraries/effect/src/main/java/androidx/media3/effect)

### Inferences
- HOOKKADR filter mapping to Media3: trim maps to `ClippingConfiguration`; scale and crop to `Presentation`/`Crop`; zoompan to a time-varying `MatrixTransformation`; lutyuv/hue/colorbalance to `RgbMatrix`/`HslAdjustment`/`SingleColorLut` or a custom `GlEffect`; drawtext to `TextOverlay`/`CanvasOverlay`; overlay (logo) to `BitmapOverlay`; amix to multiple audio sequences; sidechaincompress to a custom `AudioProcessor`. **xfade has no built-in equivalent.** Two routes exist: overlapping sequences with alpha ramps through `MultipleInputVideoGraph` and `DefaultVideoCompositor`, which preview cannot yet show reliably because multi-video-sequence CompositionPlayer is in development, or a single-sequence custom `GlEffect` that would need both frames and does not exist in the API reviewed.
- Because CompositionPlayer is experimental and its API changes between minor releases (for example, the 1.9 track-type change and the 1.10 Lottie move), a Media3 backend should pin the exact Media3 version and wrap it behind HOOKKADR's own Kotlin interface.
- Fragmentation: Transformer depends on device MediaCodec encoders, so the per-device risk of the current `h264_mediacodec` path carries over unchanged. A Media3 move does not remove the need for an encoder-fallback strategy, such as a lower resolution or bitrate retry.

## Q6. Flutter-specific: texture preview, Impeller, FragmentProgram shaders, thumbnails and waveforms, isolates, memory, background limits

### Takeaway
Video in Flutter is shown through the `Texture` widget, backed on Android by the `SurfaceProducer` API that Impeller/Vulkan requires. `FragmentProgram` shaders can only sample `sampler2D` images. However, `ImageFilter.shader` (Impeller only) can wrap a widget subtree, including a video `Texture`, which gives HOOKKADR a way to run exact per-pixel grade math in preview instead of `ColorFilter` approximations. Background export needs a `mediaProcessing` foreground service on Android 15+ (6 h per 24 h budget) and `BGContinuedProcessingTask` on iOS 26+.

### Cited Findings
- `FragmentProgram` works on both Skia and Impeller. **`ImageFilter.shader` (with `ImageFiltered`/`BackdropFilter`) works only on Impeller** and throws on other backends. For `ImageFilter.shader`, the engine binds sampler 0 to the filter input image and float uniforms 0 and 1 to its size. On OpenGLES the y-coordinate is flipped (`uv.y = 1.0 - uv.y`). — [docs.flutter.dev fragment shaders, accessed 2026-10-14](https://docs.flutter.dev/ui/design/graphics/fragment-shaders)
- Shader limits: GLSL 460 down to 100; **only `sampler2D`**; only two-argument `texture()`; no UBOs, SSBOs, vertex shaders, unsigned ints or bools; only `TileMode.clamp`; premultiplied 0–1 colors; use `FlutterFragCoord()`. Images come from decoding or from `Picture/Scene.toImageSync`. The page says nothing about external or video textures. Performance tips: precache programs (especially on Skia) and reuse `FragmentShader` instances. — [docs.flutter.dev fragment shaders](https://docs.flutter.dev/ui/design/graphics/fragment-shaders)
- Android plugins that render to a Surface must move from `createSurfaceTexture` to `createSurfaceProducer`, which "lets the Flutter engine opaquely pick the best implementation". SurfaceTexture is an opaque OpenGLES texture that breaks once Impeller uses Vulkan. Surfaces can be destroyed when the app is backgrounded, so plugins need a callback to recreate them. `video_player_android` is the reference migration. — [docs.flutter.dev: New APIs for Android plugins that render to a Surface](https://docs.flutter.dev/release/breaking-changes/android-surface-plugins); [flutter/packages PR #6456](https://github.com/flutter/packages/pull/6456)
- External textures are created outside Flutter and passed in through the `Texture` widget, with `packages/video_player` as the canonical example. — [Flutter external_textures integration test README](https://flutter.googlesource.com/mirrors/flutter/+show/HEAD/dev/integration_tests/external_textures/README.md)
- `AVAssetImageGenerator` runs the same custom video compositor when given the composition, so thumbnails can show effects. — [Apple docs: AVVideoCompositing](https://developer.apple.com/documentation/avfoundation/avvideocompositing)
- **Android `mediaProcessing` FGS:** manifest type `mediaProcessing`, permission `FOREGROUND_SERVICE_MEDIA_PROCESSING`, and "6 hours out of every 24", shared by all of an app's mediaProcessing services. At timeout the system calls `Service.onTimeout(int,int)` and the service must call `stopSelf()` within seconds or it will ANR. `onTimeout` is not available on Android 14 or lower, where reaching the timeout "immediately caches the app". — [developer.android.com FGS service types, accessed 2026-10-14](https://developer.android.com/develop/background-work/services/fgs/service-types)
- The type was introduced with Android 15. It is intended for "operations like transcoding media files". Starting another mediaProcessing FGS after the budget is spent throws `ForegroundServiceStartNotAllowedException`. — [Android 15 behavior changes](https://developer.android.com/about/versions/15/behavior-changes-15)
- Since Android 14 (API 34), every FGS must declare a type and the matching permission, and Play Console requires a declaration under Policy > App content. Apps targeting Android 15+ cannot start `dataSync` FGS from `BOOT_COMPLETED`. — [developer.android.com FGS service types](https://developer.android.com/develop/background-work/services/fgs/service-types)
- iOS 26+ has `BGContinuedProcessingTask` with Live Activity progress, plus a GPU entitlement for background GPU work (see Q3). — [Apple docs: BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)

### Inferences
- **Quick preview win:** wrapping the `VideoPlayer` widget in `ImageFiltered(imageFilter: ImageFilter.shader(gradeShader))` on Impeller would let HOOKKADR run the *same math* as `lutyuv`/`hue`/`colorbalance` in a GLSL shader. That improves on the current approximate `ColorFilter`. Exactness still depends on matching FFmpeg's YUV-domain math and color range (full vs limited) in an RGB shader; golden-frame tests (Q7) would verify it. This was not tested.
- Transitions (xfade) and zoompan in a Flutter-side preview would need two simultaneous video decoders (two `video_player` controllers) composited by a shader. That is feasible but fragile on low-end devices, and it duplicates the export logic. It cannot reach true parity with an FFmpeg export.
- Background export with HOOKKADR's minSdk 30: `mediaProcessing` exists only on Android 15+. On Android 11–14, export has to run in the foreground or under another FGS type. Which type is policy-compliant for transcoding on API 30–34 is not settled by the sources read (dataSync is the commonly used one, but that is not confirmed here).
- iOS 16–25 has no sourced long-running background export mechanism. In practice export must stay in the foreground, with `BGContinuedProcessingTask` used opportunistically on iOS 26+.
- Thumbnails and waveforms are best produced natively (AVAssetImageGenerator, MediaMetadataRetriever or Media3 frame extraction, and native PCM decoding), with small images or downsampled peak arrays passed to Dart. That keeps large buffers out of the Dart heap. This is an inference: no Flutter benchmark source was found.

### Gaps
- No source was found for Impeller default status per Android API level or device class in Flutter's October 2026 stable release, which affects whether `ImageFilter.shader` is available on all target devices.
- No benchmarks were found for SurfaceProducer vs legacy texture performance, FragmentProgram cost on video-sized textures, or memory on low-end Android devices.
- Isolate usage for thumbnail and waveform extraction was not researched with sources.
- The iOS `beginBackgroundTask` time budget on iOS 16–25 was not sourced.

## Q7. Recommended architecture for preview/export parity (one effect graph for both)

### Takeaway
The platforms' own documentation describes parity-by-construction: on Android, "the same `Composition` can be used for both preview and export" (CompositionPlayer/Transformer), and on iOS a single `AVVideoComposition` with a custom compositor serves AVPlayerItem preview, image generation and export. The recommended path is a platform-neutral render graph compiled from `EditPlan`, with FFmpeg kept as the current export backend. Preview fidelity improves first with shader-based grading and "render-preview" proxies. Native AVFoundation and Media3 backends can follow, each driving preview and export from one object.

### Cited Findings
- "The same `Composition` can be used for both preview and export." — [developer.android.com CompositionPlayer](https://developer.android.com/media/media3/transformer/compositionplayer)
- Video effects "are also supported for preview in ExoPlayer, using `ExoPlayer.setVideoEffects`". — [developer.android.com Transformations](https://developer.android.com/media/media3/transformer/transformations)
- A custom compositor is used by `AVPlayerItem`, `AVAssetExportSession`, `AVAssetImageGenerator` and `AVAssetReaderVideoCompositionOutput` whenever the `videoComposition` sets `customVideoCompositorClass`. — [Apple docs: AVVideoCompositing](https://developer.apple.com/documentation/avfoundation/avvideocompositing)
- IMG.LY markets "a single creative engine across iOS and Android" for its Flutter editor. That is the same idea delivered commercially. — [IMG.LY Flutter video editor docs](https://img.ly/docs/cesdk/mobile-editor/solutions/video-editor/flutter)
- Media3 limits: crossfade is not supported, and multi-video-sequence preview is in development. — [Composition](https://developer.android.com/media/media3/transformer/composition); [CompositionPlayer](https://developer.android.com/media/media3/transformer/compositionplayer)
- Pigeon supports async host APIs, Flutter APIs and event streams for Swift and Kotlin. — [pub.dev pigeon](https://pub.dev/packages/pigeon)

### Inferences
Proposed staged roadmap. These are engineering judgments built on the findings above.

1. **Introduce a render-graph IR now (low risk).** `EditPlan` compiles to a versioned, serializable `RenderGraph`: clips with trims and speed, transforms (zoompan keyframes), transitions (type, duration), grade parameters, overlays (text, logo with timing), audio lanes (music, voice, ducking). `render_plan.dart` becomes one *backend* (RenderGraph to FFmpeg filtergraph) instead of the source of truth. This matches CLAUDE.md's rule that AI only writes `EditPlan`.
2. **Close the preview gap cheaply while staying on FFmpeg:**
   - (a) Replace `ColorFilter` with an Impeller `ImageFilter.shader` grade shader whose math is ported 1:1 from the lutyuv/hue/colorbalance expressions.
   - (b) Add a **"render-preview" mode**: run the *same* FFmpeg graph at proxy resolution (for example 540p, hardware encoder, short segments around the playhead or per transition) and play the result. Exact parity comes for free because preview and export share an engine, at the cost of latency. Many NLEs use proxy or "render in-to-out" previews (general industry practice, not sourced here).
3. **Parity test harness:** extract frames at fixed timestamps from (i) the FFmpeg export and (ii) each preview path, and compare them with a perceptual metric such as SSIM or ΔE in integration tests on simulators and devices. This turns "parity" into a CI gate.
4. **Native engines (medium-to-long term, behind the same RenderGraph):**
   - **iOS:** `AVMutableComposition` plus an `AVVideoComposition` with a Metal/Core Image custom compositor implementing every RenderGraph node; `AVPlayer`→`Texture` for preview; `AVAssetExportSession.export(to:as:)` or `AVAssetReader`+`AVAssetWriter` for export; `BGContinuedProcessingTask` on iOS 26+.
   - **Android:** Media3 `Composition` with `Effects` (`HslAdjustment`/`RgbMatrix`/`SingleColorLut`, `TextOverlay`/`BitmapOverlay`, `MatrixTransformation`, custom `GlEffect` for transitions) and `CompositionPlayer` (experimental, version-pinned) for preview, with `Transformer` for export inside a `mediaProcessing` FGS (API 35+).
   - Write effect shaders once (for example in GLSL) and cross-compile them to Metal and GLES, or keep two hand-written versions under the golden-frame tests. The sources here do not confirm a cross-compile toolchain.
5. **Keep FFmpeg as a fallback and utility engine:** probing, unusual codecs, audio processing such as sidechaincompress and loudness, and cases the native graph cannot yet express (xfade on Media3 until custom transitions exist). Use the LGPL `_full` (or a slimmer custom LGPL) build only, and never `libopenh264` or `libx264` encoding.
6. **Commercial SDK as a buy option:** only if a headless engine API reachable from Flutter is confirmed (IMG.LY is the more likely candidate) and per-platform or MAU pricing is acceptable. Banuba's FHD default ceiling and UI-first plugin fit HOOKKADR's AI-plan model less well.

Cost and risk notes:
- Native engines double the effect-implementation surface (Metal plus GLSL) compared with one FFmpeg filtergraph, but they gain real-time preview and OS encoders.
- Media3 CompositionPlayer's experimental status and missing crossfade are the main Android risks.
- iOS AVFoundation is mature (protocol since iOS 7).

### Gaps
- No public case study or benchmark was found of a Flutter app achieving preview/export parity with native AVFoundation and Media3 backends.
- No sourced tool was found for compiling one shader source to both Metal (AVFoundation compositor) and GLES (Media3 `GlEffect`).
- The latency of the "render-preview via FFmpeg proxy" approach on HOOKKADR's target devices is unmeasured.
- No source was found on whether FFmpeg's `xfade` transition curves and `zoompan` interpolation can be reproduced bit-exactly in GLSL or Metal. Expect small numeric differences, which the SSIM-based tests would bound.
